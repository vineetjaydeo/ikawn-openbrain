Ruhi Agent Architecture: 3 Approaches

How to evolve OpenBrain from a memory/chat system into an autonomous agent platform

A

Task Queue + Worker Pool

Pattern: Like a job queue (Bull/BeeQueue style) but in-process with Postgres as the backing store.

  • DB table: tasks — stores scheduled, triggered, and on-demand tasks with cron expressions, status, next_run_at
  • Task Runner: Single interval (every 30s) checks for due tasks, executes them sequentially
  • Tools: Each task type maps to a tool function (gmail_read, calendar_create, ikawn_generate, web_search)
  • LLM decides: Task execution calls Claude with tool definitions — LLM picks which tools to use and chains them
  • Approval gate: Tasks with requires_approval pause and notify via Telegram before executing

Pros

  • Simple — fits existing Express + Postgres stack
  • No new infrastructure (no Redis, no queues)
  • Easy to inspect/debug (just query the tasks table)
  • Approval flow is just a status change

Cons

  • Sequential execution — one slow task blocks others
  • Single process = single point of failure
  • No parallel task execution without complexity
B

Agent Loop with Tool Belt

Pattern: Like OpenClaw's agent architecture — a persistent reasoning loop that wakes on schedule or trigger, thinks, acts, reports.

  • Agent Loop: A dedicated "Ruhi Agent" process that runs continuously, checking a schedule table + event triggers
  • Tool Belt: Modular tool registry — each tool is a file (gmail.tool.js, calendar.tool.js, ikawn-os.tool.js) with a standard interface
  • Planner LLM: When a task fires, Claude gets the task context + available tools + memory → produces an execution plan
  • Executor: Runs the plan step by step, pausing at approval gates
  • Sessions: Each task execution gets its own conversation context (like OpenClaw's isolated sessions)

Pros

  • True agent behavior — Ruhi reasons about HOW to accomplish tasks
  • Tool belt is extensible (add browser tool later, just drop in a file)
  • Session isolation prevents cross-task contamination
  • Natural path to full autonomy (A-mode)

Cons

  • More complex — agent loop, planner, executor are new abstractions
  • Higher LLM cost per task (planning step + execution)
  • Harder to debug when agent makes bad plans
C

Hybrid: Simple Scheduler + LLM Agent for Complex Tasks

Pattern: Two-tier system. Simple tasks run directly (no LLM). Complex tasks get the full agent treatment.

  • Tier 1 (Direct): Cron-style tasks that don't need reasoning — "fetch calendar every 2h", "check GA daily", "send cost report". Just run the function.
  • Tier 2 (Agent): Tasks that need thinking — "research competitors", "draft social content", "analyze this GA anomaly". These get Claude + tools + approval gates.
  • Scheduler: Postgres-backed, checks every 30s, routes to Tier 1 or Tier 2 based on task type
  • Tool Registry: Same modular tool files as Approach B, but Tier 1 tasks call tools directly without LLM
  • Conversational control: "Schedule X" / "Stop X" parsed by Claude in chat → creates/modifies task rows

Pros

  • Cost efficient — simple tasks cost $0 in LLM calls
  • Fast — Tier 1 tasks execute instantly, no planning overhead
  • Reliable — calendar fetch doesn't need Claude to succeed
  • Still gets full agent intelligence for complex work
  • Tool belt ready for browser extension later

Cons

  • Must classify each task as Tier 1 or Tier 2 upfront
  • Two execution paths = two sets of error handling

Recommended. This is how production agent systems work. Don't burn tokens fetching a calendar. Save the intelligence for decisions.
